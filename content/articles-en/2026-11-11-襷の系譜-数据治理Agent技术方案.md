# Tasuki Keifu: Data Governance Agent Technical Design

Version 1.0, first local implementation. Based on [the product requirements](./2026-11-11-襷の系譜-数据治理Agent产品需求.md). The design describes a new model without legacy compatibility constraints. The model has been implemented in the main site's Prisma schema and SQL migrations; the first runner is the governance-v2 CLI in the agent repository.

## 1. Architecture goals

- Treat one event as an import task containing sequential division/group batches.
- Make a batch the smallest unit that can be retried, observed, and reported independently.
- Give person/organization normalization, membership governance, and person-fact verification explicit subgraph contracts. The runner uses deterministic scheduling, not LLM orchestration.
- Separate raw input, decisions, evidence, and actual writes so each result can be explained.
- Make database writes retryable and idempotent. Process failure must not lose an import or repeat a destructive operation.
- Restrict external research to serious identity ambiguity and membership conflicts that rules cannot explain.

## 2. System boundary

```text
Import tool / API
  -> Event task runner + governance runtime database
       -> sequential batch graphs
            -> organization/person normalization
            -> membership governance
            -> person-fact verification
       -> read current business data
       -> atomic business writes and business audit
       -> batch alerts and event summary email
```

- **Import adapter:** accepts existing payloads, preserves raw input and source identity, and parses event/division/group keys. It does not make entity-governance decisions.
- **Event runner:** creates the event task, advances batches in sequence, handles retries, and schedules the event summary. Scheduling is ordinary application code.
- **Governance graph:** makes domain decisions for one batch and returns structured results, evidence references, findings, and proposed changes.
- **Business writer:** validates the plan, idempotency key, and target versions; writes business data and audit records; returns actual outcomes.
- **Governance store:** records lifecycle and diagnostics; it is not authoritative for business facts.
- **Business database:** remains authoritative for people, organizations, memberships, and results.

## 3. Compact persistence model

The model stores enough information for recovery, explainable decisions, and business-change audit without permanently duplicating every import row, evidence document, or internal graph state.

| Entity | Purpose |
| --- | --- |
| `EventImportTask` | Tracks intake, queueing, batch progress, and event summary. `requestKey` is unique. |
| `GovernanceBatch` | One division/group with sequence, immutable payload reference, content hash, status, and summary. |
| `BatchAttempt` | Initial run, recovery, or retry; includes input fingerprint, checkpoint reference, errors, and aggregate metrics. |
| `AgentExecution` | Agent identity/version, status, concise outcome, evidence references, and resource metrics for an attempt. |
| `GovernanceFinding` | Non-trivial issue, severity, resolution state, confidence, reason, and compact evidence/details. |
| `GovernanceChange` | Proposed/applied business mutation, stable change key, idempotency key, patch, evidence references, and business audit reference. |
| `NotificationDelivery` | Deduplicated batch alert or event summary, delivery state, retry timing, and error. It belongs to exactly one task or batch. |

`GovernanceFinding` and `GovernanceChange` are independent: a routine inference can produce a change without a finding, while an unresolved finding may have no executable change. A database XOR constraint enforces notification ownership.

### Fields, constraints, and retention

Keep IDs, foreign keys, state, idempotency keys, hashes, and timestamps as queryable columns. Put agent-specific evidence and supplemental details in JSON, validated against application catalogs. Do not store a full prompt, graph state, webpage, PDF, or business-entity snapshot by default.

Store one immutable compressed raw payload per division/group and keep only its URI, byte count, and hash in SQL. Findings describe non-trivial issues; changes contain only the relevant patch. The business `AuditLog` remains authoritative for successful writes. Checkpoints are recovery data, not permanent audit: clean successful/obsolete checkpoints after the recovery window while retaining unresolved summaries, applied-change indexes, and audit references.

Suggested states are `queued/running/completed/completed_with_unresolved/failed` for tasks and batches; `running/succeeded/partial/failed/superseded` for attempts; `running/succeeded/skipped/partial/failed` for agent execution; `resolved/unresolved/informational` for findings; `planned/applying/applied/failed/superseded` for changes; and `pending/sending/sent/failed` for notifications. Unique constraints cover request keys, batch unit and order within a task, attempt number, execution number, change identity/idempotency, and notification deduplication. Worker indexes cover status, scheduling time, and expired leases.

At the field level, a task carries its request key, source/event references, manifest, status, summary, scheduling and worker lease/heartbeat timestamps, and terminal error. A batch carries unit type/key, sequence, payload reference/hash/size, record count, status, and summary. Attempts include attempt number, trigger type, input fingerprint, checkpoint thread, timestamps, error, and metrics. Executions include stable agent key/version, execution number, input/result summaries, evidence references, and LLM/network counts and latency. Findings carry finding key/code, subject reference, severity, resolution, confidence, reason, and evidence details. Changes carry change key/revision, globally unique idempotency key, operation/entity reference, state, patch, evidence, and business audit ID. Notifications carry exactly one task or batch owner, kind/dedupe key, payload, attempts, next retry, lease, and delivery/error timestamps.

The governance model lives in a separate PostgreSQL `governance` schema in the main site's database. Governance tables do not have strong foreign keys to business entities. The writer uses one PostgreSQL transaction across schemas for business rows, business audit, change status, and cache invalidation outbox.

## 4. Runner and graphs

The event runner persists all input first, processes batches by sequence, and reads business state again for each batch. After a successful batch commit it proceeds to the next. Technical failures receive bounded retries and may stop later batches; unresolved findings are normal outcomes and do not stop the event. If shutdown occurs after commit but before finalization, the runner recognizes the completed batch and repairs attempt/notification state without repeating business writes.

The `governance_batch_graph` loads current context, normalizes organizations, normalizes people, conditionally runs membership governance, conditionally verifies person facts, then aggregates the plan. The graph returns a plan; writing occurs outside it.

Batch state carries the persisted input reference, current business context, agent outputs, evidence references, proposed changes, findings, and aggregate summary. Conditional routing checks for membership clues/existing memberships and supplied birthplace/PB fields. Node names correspond to business stages rather than every helper, keeping checkpoints useful without persisting each deterministic helper transition.

### Normalization

Organization and person identity use separate sequential subgraphs. Resolve source mappings and confirmed aliases first. Exact rules and history are preferred. A common organization abbreviation can receive constrained non-web semantic matching and, when confirmed, be saved as an alias. Web research is reserved for material competition between identity candidates. Merge/split operations require evidence and explicit relationship scope; collisions in results or team associations remain unresolved. If no candidate is supported, create a source-scoped entity rather than forcing a match.

For people, use stable source keys, normalized names, birth dates, and school history. Existing high-school history may help identify a new university record. A clear contradiction in the current university timeline prevents an automatic same-person match.

### Membership governance

The membership subgraph collects candidates and anchors, parses source dates, infers supported academic windows, applies explicit employment/team exclusivity rules, and records genuine unresolved conflicts. Japan's school year begins in April; high school is normally three years and university four, but duration is not proof of graduation. Source dates can replace inferred dates; inferred dates only fill gaps. Do not infer a school, ongoing status, or a completed transition from missing data. New corporate-team membership does not automatically end a prior relationship.

### Person facts

The person-facts subgraph only runs when birthplace or personal-best input is present. It accepts a birthplace only from a sufficiently reliable source when the current field is empty. A new personal best must have a clearly parsed event/result, a source reliability of at least 3, and reliability no lower than the value it would replace. Fuzzy results, unknown event types, or weak sources do not overwrite existing values. Routine governance does not attempt to repair a known incorrect PB; that requires a dedicated correction workflow.

Each subgraph receives a batch context and returns structured changes, findings, executions, and evidence references. The aggregate node deduplicates stable change keys and produces counts and a human-readable summary.

## Intake and result contracts

The CLI accepts a strict Zod manifest with schema version `event-governance/1`, a `requestKey`, event-edition reference, mode, and ordered batches. Each batch includes `unitType`, unit key and sequence, source ID, race slug, organizations, and rows, with teams optional. Missing affiliation, dates, or personal bests may be valid; malformed structure, duplicate source keys, or unknown organization references are rejected. An input hash prevents reuse of one request key with different content.

The plan identifies batch/race/source/edition and mode, then includes changes, findings, agents, and summary. Its finite operation catalog covers person/organization creation, source mapping, name variants, memberships, person facts, personal bests, race/team results, and scoped person/organization merge or person split. Research requests are limited to person identity, organization identity, or membership conflict, with an allowlisted ID set and structured output. Arbitrary SQL and arbitrary field patches are not exposed.

## 5. Writes, idempotency, and recovery

The graph persists a plan before the writer applies it. The writer validates allowed operations, target state, input fingerprint, and optimistic versions. In one database transaction it applies business changes, writes business audit records, marks governance changes applied, and records cache invalidation. External LLM, web, and SMTP calls never run inside this transaction.

Every operation has an idempotency key. If a process dies after commit, a retry reads the applied change and does not repeat it. If business data changed after planning, mark the plan stale and re-read context before replanning. A merge or split is restricted to explicit IDs and relationship scopes; unexpected associated results or records cause an unresolved outcome rather than silent data loss. Dry-run saves a plan but never writes business data.

## 6. Research and resource controls

Only identity ambiguity and membership conflicts may request web research. Each request receives an allowlisted candidate set and a structured output schema. A cited URL must have appeared in tool results; this prevents fabricated citations but does not prove the source itself is correct. Non-web semantic judgments are limited to `match`, `distinct`, or `unresolved`.

The first-release budget is at most three research requests per batch, 25 seconds per request, 24,000 input characters, 3,000 output tokens, and two tool calls per request. Budget is reserved durably per attempt so checkpoint recovery cannot reset it indefinitely. The model is selected explicitly through configuration. Without a configured model, record insufficient research and leave deterministic governance operational; do not guess a model or account.

## 7. Reporting, dashboard, and notifications

Send a batch alert for serious unresolved issues and technical failures. Send an event summary when all batches finish. Notification delivery is asynchronous and deduplicated; retry with backoff and a lease. SMTP acceptance followed by a local crash can still cause a duplicate, so delivery is at-least-once rather than exactly-once.

The personal-site dashboard reads a dedicated read-only database connection, uses separate HTTP Basic Authentication, and fails closed if credentials are missing. It displays bounded recent tasks and summaries, evidence links, minimal before/after details, audit references, and delivery status. It does not expose raw payloads, full plans, prompts, credentials, or checkpoints. The API limits the number of tasks, batches, and related records returned.

Metrics distinguish planned from applied rows and repairs. Imported rows count only after a successful apply; dry-run totals are separate. Repair counts measure operations, not unique people, and event summaries aggregate completed batches without double-counting retries.

## 8. Security and operational safeguards

Use a dedicated least-privilege database role for dashboard reads; it cannot write governance tables or access unrelated user feedback. Validate strict manifests and reject duplicate keys, unknown organization references, malformed rows, and unsupported operations. Preserve the caller's original file on validation failure. Protect payload storage against path traversal and symlink escapes, verify hashes, and enforce a decompression limit. Use worker leases and fencing tokens so an expired worker cannot commit after a newer worker takes over. Do not return credentials, raw input, or full internal traces from observability endpoints.

## 9. Delivery and validation stages

1. Land the schema, migration, payload store, runner, and deterministic governance paths; test atomic writes, retry, checkpoint recovery, and read-only access.
2. Pilot one real incremental event, one division/group at a time. Start with dry-run and a small explicit apply, then inspect records, audit, cache invalidation, and reports.
3. Expand only after verifying source quality, batch size, storage growth, model/network budget, and operational recovery. Historical scans remain a separate decision.

Initial acceptance includes sequential batches, correct membership inference, no personal-best regression, dry-run/write gates, cross-process checkpoint recovery, stale-worker fencing, malformed-input rejection, unresolved continuation, transaction rollback, notification retry, and scoped merge/split behavior.

## 10. Decisions to validate during implementation

Measure real payload size, checkpoint growth, event batch counts, storage lifecycle, and database grants before setting retention. Confirm the production database's transaction and cache invalidation behavior. Verify email retry semantics, real provider/model availability, and a real event pilot; fixture tests alone do not prove these external integrations.

## 11. Existing code baseline

The first implementation reuses the business models and audit system, while governance runs in an isolated schema and repository boundary. It does not require compatibility with legacy governance tables. Existing business records retain source evidence and explicit date-basis/end-state fields; the governance schema owns task lifecycle, agent execution, findings, changes, and notification state.

## 12. Implementation notes

The production intake contract is a strict `event-governance/1` manifest containing a request key, event edition, mode, and ordered batches. Each batch identifies its unit, source, race, organizations, rows, and optional teams. Missing affiliation, dates, or personal best may be valid; malformed structure, duplicate keys, and unknown organization references are not. The caller's original input is retained when validation fails.

The plan contains changes, findings, agent summaries, and batch summary. The controlled operation catalog covers person/organization creation, source mapping, name variants, memberships, person facts, personal bests, race/team results, and scoped person/organization merge or split. It does not expose arbitrary SQL or arbitrary field patches.

Implementation proceeds from schema and migration to payload persistence, intake/lease handling, graph nodes, business writer, notification queue, and read-only observability. Validate each boundary with focused unit and PostgreSQL integration tests before the real pilot.

## 13. First-release implementation contract

The first release uses an immutable gzip payload addressed by hash in a persistent absolute directory. SQL stores its reference. Reads verify the hash, guard paths and symlinks, and cap decompression at 64 MiB. LangGraph checkpoints use a separate `governance_checkpoint` schema. Successful or superseded attempts are eligible for cleanup seven days after task completion; failed-task recovery points remain. Raw inputs and governance audit are not automatically deleted yet, so a production retention window remains an operational decision.

The task and batch states are `queued`, `running`, `completed`, `completed_with_unresolved`, and `failed`; the schema retains `partial` as an extension point, but the first release does not produce partially committed business transactions. A resumed attempt uses its graph thread; a stale plan starts a fresh context. Changes are `planned` or `applied` in normal operation, while obsolete plans become `superseded`. Dry-run leaves changes planned.

Initial rules include source-key and alias reuse; normalized names; source-scoped creation when identity is uncertain; academic-year inference only from reliable anchors; no automatic closure of old memberships; evidence-gated PB improvements; conservative birthplace backfill; and unresolved findings when research is unavailable, over budget, or inconclusive. The system does not claim that all PBs on the site are current.

The site queries a bounded number of recent tasks and related records. It shows summaries, evidence links, minimal before/after values, business audit references, and notification status only. A dedicated read-only database role and fail-closed authentication protect access. Deployment must configure the read-only connection and authentication secrets; their values are never part of the article or API response.

## 14. Local verification and pilot boundary

- Thirteen rule/research fixture tests and thirteen real PostgreSQL integration tests passed.
- All 20 main-site migrations ran in order against a disposable empty database, with no extra schema drift.
- Coverage included sequential two-batch import, bidirectional membership inference, no PB regression, dry-run, write gates, cross-process checkpoint recovery, post-commit crash, stale-worker fencing, invalid input, unresolved continuation, full transaction rollback, notification retry, merge/scoped split, and stale-plan replanning.
- The read-only grant script passed locally: the site role can read governance data but cannot write governance tables or access user feedback; the business read-only role cannot write people.
- Type checks passed across three repositories; production builds passed for the main and personal sites. The personal-site build also reported a pre-existing missing `eslint-plugin-react-hooks` dependency, so this does not establish a successful lint run.
- Model responses, web research, and mail transport used fixtures. No paid-model research, live web research, real email delivery, or production migration was performed. A real event pilot, deployed storage/permissions, and research quality remain to be verified.

The repository runbooks describe deployment order: migrate the main site, initialize checkpoint schema and grants, deploy worker/read-only site, then use a named event for dry-run and a small apply. The technical test results above are local results, not production validation.
