# Tasuki Keifu: Data Governance Agent Product Requirements

This document defines the goals, governance scope, workflow, and outcome requirements for the Tasuki Keifu data governance agent. It is the requirements baseline for implementation. Confirmed decisions belong in the relevant sections; unresolved items remain in the source requirements until decided.

Related: [Technical design](./2026-11-11-襷の系譜-数据治理Agent技术方案.md).

Updated November 13, 2026: the two-pass DAG, bounded cross-check, compact input, historical-entry identity rule, and per-item lightweight validation are deployed. This revision made no live model request, batch rerun, or import. Production benefits remain unmeasured. Each domain still sends all unresolved objects in one group in one lightweight request. See the [optimization history](./2026-11-12-襷の系譜-数据治理Agent优化记录.md).

## Identity evidence and recoverable uncertainty

A unique exact kanji/kana candidate may match by rule when a sourced historical entry from a different race is no later than the current race and uses the same independently canonicalized organization ID. Reject known cohort contradictions and competing Membership-based candidates. Missing Membership alone is neither a conflict nor a reason to research. Similar organization strings with unconfirmed IDs do not satisfy this rule.

DNS registration can support identity under those guards, but never proves a start or creates grade/Membership facts. DNS alone triggers neither lightweight nor deeper research. A weaker same-kana/different-kanji candidate remains visible to cross-check without alone blocking strong evidence. A high-school-to-university transition alone proves neither identity nor a contradiction.

A person lightweight match without independent evidence belonging to the selected target, unless an explicit birth date matches, becomes per-item unresolved with the original verdict context retained in a warning. Preserve valid peers and proceed to cross-check. Malformed batches, fabricated references, foreign targets, and explicit birth-date contradictions remain blocking. Cross-check receives both domains’ lightweight decisions, rule evidence, and validation warnings.

The dashboard leads with readable states, stage funnels, failures, and actual call totals; raw metrics expand on demand. Failed batches retain completed work, unknown values remain unknown. Batch alert titles identify the event and division/group; event-summary titles identify the event.

## Goal

Use event imports as the primary governance entry point so that new data also improves the existing records it touches. The agent should normalize entities, maintain histories, and update facts when rules and evidence support a decision. Difficult cases may receive bounded research. When the evidence is insufficient, preserve the best current result and original material, and clearly record what remains unresolved.

People should mainly intervene when a business rule is wrong, the agent workflow needs adjustment, or the data model cannot express the domain, rather than approving ordinary results row by row.

## Scope and principles

### Entry point and unit of work

- Event import is the main trigger; a full-database scan is not a prerequisite.
- An **event import task** covers one event. A **governance batch** covers one division or group within that import.
- Process the real import unit, usually one division or group per batch. Finish and write one batch before starting the next.
- Each batch reads current business data, so later batches can use earlier committed results.
- Backfill is primarily done incidentally during imports. Targeted scans and reruns after rule changes are later capabilities, not first-release prerequisites.

### Governance record model

- Keep governance execution state separate from business fields on Person, Organization, and Membership.
- The independent model must represent event tasks, division/group batches, agent execution states and results, plus necessary write and audit records. Exact entities and storage boundaries are defined in the technical design.
- Design the new model from current requirements. Legacy agent tables, enums, and data shapes do not constrain it.
- Historical-run migration and backward compatibility are later upgrade decisions; they may be omitted and must not distort the new model.

### Agent responsibilities

The first release uses three responsibility groups, with no separate event agent or LLM orchestrator.

| Agent | Responsibility |
| --- | --- |
| Person and organization normalization | Map imported people and organizations to the right entities; identify duplicates, incorrect links, homonyms, and aliases. Both entity types are in scope. |
| Membership governance | Handle school, university, corporate-team, and other organization memberships; infer supported academic-year windows from reliable anchors; identify genuine conflicts. |
| Person-fact verification | Handle person facts such as birthplace and personal bests when present. Trigger only when relevant fields are supplied. |

### Batch workflow

Within each batch, normalize organizations first, then people, using deterministic rules and batched lightweight judgments. Run the bounded cross-check described below before any remaining serious identity research. Use the final identities for membership governance, followed by person-fact verification. Skip a downstream agent when the input has no relevant fields. Aggregate results and execute the write plan only after governance completes.

### Graph baseline

- Use one deterministic event runner and one governance graph per batch.
- The runner sequences batches and manages persistence, retries, writes, and notifications. It is ordinary program code, not an LLM agent.
- Use dedicated subgraphs for normalization, memberships, and person facts.
- A domain node may use deterministic rules first, followed by a bounded LLM or web-research call only when policy allows it.
- Persist intermediate state at meaningful boundaries for recovery. Do not create a checkpoint for every helper function.

### Two-pass normalization and a bounded cross-check

The first dry-run of the ordinary 333rd Nittaidai meet, men's 5000m heat 1, contained 44 rows and produced 17 unresolved identities. These are not 17 confirmed conflicts. Read-only sampling found candidates with historical results under the same affiliation but no Membership, and organization-name variants that affected person matching. The current workflow underuses this evidence; the findings do not prove that all candidates should be merged.

Rules run first. Pass one batches the remaining unique organization or person observations for lightweight, non-web LLM judgments using existing evidence. Outcomes are match, distinct, or unresolved. Lightweight means a narrow task and compact context, without requiring a different model. Pass two performs bounded deeper research only for remaining serious identity ambiguity; missing fields alone never justify web research.

A dedicated LLM cross-check reviews organization and person conclusions, evidence, and dependencies. It proposes structured issues and actions, not database writes or unrestricted agent calls. Code controls the fixed sequence: initial organization normalization → initial person normalization → one cross-check → at most one organization adjudication → at most one reassessment of affected people → remaining serious research → final plan. There are no backward edges, and unresolved cases are valid outcomes.

Person matching may expose an organization issue, but an organization correction needs evidence independent of that disputed person's identity. Do not assume two observations are the same person to prove their organizations equivalent, then use that equivalence to prove the person match. Membership and person facts consume final mappings; all business writes remain centralized. DNS is registration evidence, not proof of participation. Do not invent grade or Membership from a school name, or collapse ordinary meets and NCG into one competition meaning.

Each group review must consider explainable judgments that could become rules. Distinguish general rules from confirmed entity-specific aliases and source mappings; there may be no rule worth adding in a round. A supported match between 大東第1高校 and 大東大一高校 belongs in that school's aliases, not a universal substitution between 第1, 一, and 大一. Proposed rules need conditions, counterexamples, evidence, and regression checks. Operators must improve the agent rather than manually resolve rows on its behalf.

Observe per-stage input/resolution counts, unique objects, batch sizes, cross-check issues, organization corrections, affected/reassessed people, and identities resolved by organization corrections, alongside versions, calls, tokens, cost, duration, and final unresolved outcomes. Fewer calls or unresolved cases alone do not establish success. Reviews remain user-led; no separate report document is required after every run.

### Import and write principles

- Preserve the original payload and source-row identity.
- Uncertain fields may remain empty; structural corruption and invalid references must fail validation rather than be silently dropped.
- Commit a batch's business changes atomically. A failed transaction leaves no partial business writes.
- Use stable idempotency keys and optimistic version checks. Replanning after concurrent changes must use fresh context.
- Persist unresolved outcomes without blocking later divisions/groups. Technical failures receive bounded retries and can stop subsequent batches.
- Provide dry-run and explicit write controls.

### Research boundaries

- Web research is limited to serious person/organization identity ambiguity and membership conflicts that rules cannot explain.
- Ordinary organization abbreviations may use a constrained, non-web semantic judgment.
- Research must use a bounded candidate set, cite returned source URLs, and return structured conclusions.
- Never invent a match or resolve a material conflict without evidence. When calls fail, time out, or exhaust budget, record why research stopped and continue with the best evidence available.

### Membership baseline

- Academic-year boundaries follow Japan's April school year. High school and university durations may support inference only when an anchor is reliable.
- A sourced date may correct an inferred date; an inference only fills a missing value.
- Do not infer a school, graduation, or current employment state from missing dates alone.
- Preserve ordinary gaps and incomplete memberships. Do not close an earlier team membership merely because a new corporate team appears.
- Record true contradictions and unresolved conflicts; do not force a timeline to look complete.

### Reporting and observability

- Send a batch alert for serious unresolved cases and technical failures; continue after ordinary unresolved cases.
- Send an event-level completion summary describing import and governance totals, affected people/organizations/memberships, and unresolved counts.
- Explain unresolved items in natural language, including the current handling and why further research stopped.
- Keep a read-only operational view for recent tasks, batches, findings, changes, and notification status. Do not expose raw payloads, prompts, credentials, or unrestricted database access.

### First validation sequence

- Start with an available incremental event import, not a full historical scan or replay.
- Select an event that can be imported division by division or group by group.
- Observe agent coordination, writes, and reports across sequential batches before deciding whether to add historical cases or targeted backfill.
