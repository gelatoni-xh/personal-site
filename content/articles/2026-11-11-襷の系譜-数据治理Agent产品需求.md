# 襷の系譜：数据治理 Agent 产品需求文档

本文定义襷の系譜数据治理 Agent 的产品目标、治理范围、运行流程和结果要求，并作为后续方案完善与实现的需求基线。后续确认的决策直接更新本文；尚未确认的事项列入文末，确认后移入相应章节并从待确认项中移除。

## 目标

以赛事数据导入为主要治理入口，让新数据进入系统时同时改善本次涉及的存量数据。Agent 根据已有规则和证据自动完成可判断的归一化、履历处理和资料更新；少数严重疑难可以继续研究，无法判断时也先保存当前最佳结果和原始资料，并清楚记录未解决之处。

人的主要介入点是发现业务规则不合理、Agent 流程需要调整，或现有数据模型无法表达业务，而不是逐条批准普通治理结果。

## 产品范围与原则

### 入口与处理粒度

- 赛事导入是主要触发入口；不以先扫描全库作为启动前提。
- 术语区分：**赛事导入任务**指一场赛事的整体导入；**治理批次**指其中一个区或组的一次治理与写入。整场赛事可以包含多个依次执行的治理批次。
- 按赛事的实际导入单位处理，通常是同一区或同组作为一个治理批次。该批次完成治理并写入后，再处理后续区或组。
- 每个批次读取当前数据库，因此后续批次可以利用前面已治理并写入的数据。
- 存量治理主要由导入顺带完成。定向存量扫描和规则升级后的补跑可以作为后续能力，不构成首期主流程。

### 治理记录模型方向

- 治理运行记录采用独立于选手、组织和 Membership 业务字段的治理模型；不在各业务实体上堆放 Agent 最近处理时间、运行状态等字段。
- 独立治理模型需要表达赛事导入任务、区/组治理批次、批次内各 Agent 的处理状态与结果，以及必要的写入和审计记录。具体实体关系、字段及存储边界待整体模型设计后确定。
- 新模型完全从当前产品需求出发，不受旧 Agent 库表、字段、枚举或既有数据形态约束；以新版本模型的清晰性和完整性为最高优先级。
- 旧数据兼容、历史运行记录迁移和升级路径不属于当前产品模型设计范围，留待后续技术方案阶段处理；允许届时确定为不兼容或不迁移。

### Agent 分工

首期按三组 Agent 设计，不单设赛事 Agent，也不单设编排 Agent。

| Agent | 职责 |
| --- | --- |
| 选手与组织归一化 Agent | 将导入中的选手和组织映射到正确实体；识别重复、误挂、同名、别名等归一化问题。选手和组织是确定纳入的对象。 |
| 履历 Agent | 处理学校、大学、实业团及其他组织的 Membership；根据可靠锚点补全可推算的学年窗口；识别真正冲突的履历。 |
| 人物事实核验 Agent | 处理人物出身地、PB 等原始数据中可能出现的人物事实。字段经常缺失，按需触发，优先级低于归一化和履历治理。 |

赛事和赛果错误概率相对较低且较容易人工发现，首期不设专门赛事 Agent；必要的确定性检查仍可作为普通导入逻辑存在。

### 批次内流程

```text
本区/本组原始资料 + 当前数据库
  → 选手与组织归一化
  → 履历 Agent 按需处理
  → 人物事实核验 Agent 按需处理
  → 写入本批当前最佳结果
  → 生成站点观测记录和简明汇报
  → 处理下一批
```

三个 Agent 共用同一批次的资料和处理上下文，按依赖顺序传递结果；共用上下文不意味着每个 Agent 每批都必须调用。履历和人物事实处理不得因少数身份疑难而阻塞整批。后续批次发现前序判断可能需修正时，按新的治理修正处理并记录影响；首期不设计跨批次自动回滚和全量重跑。

### Graph 架构基线

- 赛事导入任务由普通 runner 控制；runner 按顺序创建并执行赛事下的各区/组治理批次，不增加 LLM 编排 Agent。
- 每个治理批次运行独立的治理流程 Graph，并按依赖顺序调用各职责子图：选手/组织归一化、履历治理、人物事实核验。
- 选手与组织属于同一归一化阶段，但分别使用专用子图，以适应不同的证据和判断规则。
- runner 根据批次输入和依赖结果决定是否调用子图；没有相关输入或无需处理时跳过，不要求每批固定调用全部 Agent。
- 单批写入完成后继续下一区/组；单批有需关注问题时发送批次邮件，整场赛事完成后发送赛事汇总邮件。

### 导入和写入原则

- 导入资料应进入系统治理；不能因初步异常、候选不唯一或 Agent 无法完全判断而拦截或丢弃原始数据。
- 先保留原始资料及来源，再由 Agent 根据规则和证据写入当前最佳判断。治理状态不完整不等于数据不写入。
- Agent 在授权的治理范围内自动判断并写入，不要求人逐条确认普通结果。
- 选手档案有足够证据支持时，Agent 可以自动合并或拆分，并记录判断依据及受影响数据；证据不足时不阻止导入，仍写入当前最佳归属，并将严重身份疑难记录为 unresolved。
- 对可靠既有值的修正应有依据并可追溯；推算值只补空，不覆盖已有可靠来源值。
- Agent 发现的问题若揭示业务规则或数据模型本身可能有误，应记录为需要产品/模型判断的 unresolved，而不是隐去矛盾或假装确定。

### 网络研究边界

联网研究不是普通字段补全步骤。主要用于会造成严重影响、且现有数据和规则无法解决的疑难：

- 选手/组织归一化疑难，例如可能把不同选手/组织合并，或把同一选手/组织拆成多个实体。
- Membership 冲突，例如互斥关系、时间线矛盾、转队归属等无法按既定规则解释的情况。

以下情况默认不启动网络研究：普通所属缺失、PB 不清晰或不是必要更新、原始资料未提供的普通字段、已有规则可以解释的情况、不会改变治理结论的低价值疑问。新数据与现有数据一致时直接处理，不为确认而重复查询。

选手/组织归一化的研究触发条件是：现有来源和规则无法消解身份疑难，且存在不同实体可能被错误合并、或同一实体可能被拆成多个档案等严重错误风险。姓名差异、候选数量或普通字段缺失本身不构成联网理由。Membership 的研究触发条件是：关系按业务应互斥或时间线存在实质矛盾，且无法用现有规则解释；两个组织关系并存或日期不完整本身不构成冲突。

研究以解决具体疑难为目的，不追求绝对真相或穷尽所有网络来源。找到足以支持当前判断的证据即可；若资料太少、来源冲突、任务范围过大或继续查询价值低，则停止研究，写入当前最佳判断并记录 unresolved 的原因。来源本身也可能有误，结论应反映证据和置信程度。

### 履历规则基线

- 已有规则能够推算的高中、大学等学年窗口，可在有可靠时间锚点时补全。
- 高中履历时间未知、但大学开始节点明确时，可按既有学制规则反推大学开始前的高中三年窗口；例如大学从 Y 年 4 月 1 日开始，对应高中窗口为 Y-3 年 4 月 1 日至 Y 年 3 月 31 日。
- 推算只补空，不覆盖已有可靠来源日期。
- 已有 Membership 且新来源没有额外信息时跳过；所属明确但日期未知时可以写入关系并保留未知日期。
- 学校、实业团、俱乐部及其他组织关系需按实际业务判断是否互斥；不能把所有重叠一概视为冲突。
- 学校、大学经历的衔接推算和按比赛日期/年级确定学年，沿用历史资料中已有规则，后续结合真实导入样本复核完善。

### 报告与观测

报告分为两类：

- **站点观测 / 日志**：面向运行追踪，记录赛事导入任务、各治理批次、Agent 处理状态、写入和修复、unresolved、证据来源及运行信息。现有观测站点可以重做，不要求兼容旧版展示；旧 trace 和审计记录可作为参考。
- **治理批次邮件**：单个区/组批次默认不发邮件；发现需要关注的问题时才发，例如严重归一化疑难、无法解释的 Membership 冲突、Agent 失败或其他需及时处理的异常。普通规则修复不单独触发批次邮件。具体告警分类、阈值和重试策略在模型设计中确定。
- **赛事汇总邮件**：整场赛事的导入任务结束后必须发送，概括本次导入及治理做了什么，包括导入量、修复量、涉及的人物/组织/履历和 unresolved 数量。未解决项用自然语言说明问题、当前处理结果和停止继续研究的原因。

### 首期验证顺序

- 首轮使用可供导入的赛事增量验证治理流程；不先启动全量存量扫描，也不以历史回放作为首轮入口。
- 首批选择有明确分组或分区、可逐组/逐区导入的赛事；每批完成治理和写入后再处理下一批。
- 通过增量批次观察 Agent 协作、写入结果和报告表现后，再决定是否使用历史案例补充验证，以及何时开展定向存量治理。

## 后续技术方案设计范围

产品方向已确定。以下内容进入技术方案阶段设计，不构成待确认的产品方向：

- 独立治理模型的实体关系、字段、状态流转和存储边界。
- 原始导入证据、治理结论、置信度、原因枚举与补充 JSON 的具体结构。
- Agent Graph 节点、状态传递、提示词/规则配置、触发去重、重试和批处理机制。
- LLM 成本、网络调用预算、剪枝、缓存、并发和性能优化。
- 站点观测页面的实现方式，以及批次告警分类、阈值和重试策略。
- 技术部署升级方案；旧数据兼容或迁移可以不做，且不得反向限制新模型。
- 首批增量赛事的技术接入方式与验证指标。
