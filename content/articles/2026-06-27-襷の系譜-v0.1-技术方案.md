# 襷の系譜 V0.1 技术方案

日期：2026-06-27

关联文档：[2026-06-27-襷の系譜-v0.1-PRD.md](./2026-06-27-襷の系譜-v0.1-PRD.md)

## 1. 技术目标

V0.1 的技术目标是支撑一个小而可信的选手资料站：

- 以选手档案为核心页面
- 支持日文主体验，中文和英文保留界面框架
- 支持青山学院大学、國學院大學、中央大学的学生名单录入
- 支持 PB、箱根出场记录、来源、确认状态等数据
- 支持从选手跳转到同大学、同高中、同年级选手
- 支持后续扩展到更多大学、高中、实业团、赛事和成绩库

V0.1 不追求复杂架构。优先级是：

1. 数据模型清楚
2. 数据可维护
3. 页面可读
4. 来源可追溯
5. 后续可演进

## 2. 技术栈选择

### 2.1 应用框架

采用：

- Next.js
- React
- TypeScript
- App Router

理由：

- 前后端一体，适合个人项目快速推进
- SSR/SSG 能支持资料站和 SEO
- API Route / Server Action 足够支撑后台管理和数据查询
- TypeScript 有利于长期维护数据结构
- 后续部署到 Vercel、自有服务器或 Docker 都比较顺滑

### 2.2 样式与组件

采用：

- Tailwind CSS
- shadcn/ui
- lucide-react

理由：

- 适合快速搭建克制、清爽、资料馆风格的界面
- 表格、表单、弹窗、标签、Tabs 等基础组件容易复用
- lucide-react 能满足搜索、筛选、外链、语言切换、来源等图标需求

视觉方向：

> Archive, not Dashboard.

界面应像现代化选手名鉴和资料馆，不做新闻站，也不做复杂数据大屏。

### 2.3 数据库

采用：

- PostgreSQL
- Prisma ORM

理由：

- 项目早期最重要的是实体、关系、来源、状态和约束
- PostgreSQL 适合做主业务库
- Prisma 能提供清晰 schema、迁移、类型生成和开发体验
- 后续可以平滑增加全文搜索、物化视图、分析同步等能力

明确不在 V0.1 使用：

- Neo4j
- ClickHouse
- BigQuery
- 独立数据仓库
- 独立图数据库

关系图和关系跳转在早期完全可以由 PostgreSQL 查询支撑。

```text

```

## 4. 数据建模原则

### 4.1 宽收集，窄展示

V0.1 页面展示可以很克制，但数据收集应尽量完整。

原因：

- 大学官网、箱根官方、NTV、月陸、粉丝站提供的字段各不相同
- 部分字段当前不用，后续可能成为关系探索、筛选或专题内容的基础
- 对个人项目来说，早期字段略多的成本低于后期反复补历史数据

原则：

- 能稳定确认的公开事实可以收
- 不确定字段可以收，但必须标注状态
- 粉丝向字段可以收，但默认不作为核心展示
- 每条重要数据尽量关联来源

### 4.2 关系优先于页面

数据模型应优先表达实体之间的关系，而不是只服务当前页面。

重点关系：

- 选手属于大学
- 选手出身高中
- 选手曾经属于某组织
- 选手参加某届赛事
- 选手在某区间有成绩
- 选手拥有某项目 PB
- 数据来自某个来源

V0.1 的页面很少，但模型要能支撑：

- 同大学
- 同高中
- 同年级
- 高中到大学流向
- 大学到实业团流向
- 赛事出场历史

### 4.3 来源和确认状态是一等数据

数据站的可信度来自来源和校验，而不是字段数量。

所有关键事实都应支持：

- 来源 URL
- 来源名称
- 来源类型
- 抓取或录入日期
- 确认状态
- 备注

建议确认状态：

- `verified`：已确认
- `pending`：待确认
- `conflicting`：存在冲突
- `missing`：缺失

### 4.4 多语言以原文为核心

日文是主语言和事实原文。

多语言策略：

- 日文名称作为主名称
- 中文和英文作为翻译或辅助展示
- 罗马字、读音、旧字体、简称、媒体常见写法作为 name variant 管理
- 不要求 V0.1 翻译所有数据

## 5. 核心数据域

### 5.1 Person：选手/人物

用于表示选手、教练、监督、主务等人。

V0.1 主要使用选手，后续可扩展到教练和工作人员。

建议收集字段类型：

- 姓名
- 读音
- 罗马字
- 中文译名
- 英文名
- 生年月日
- 年龄
- 出身地
- 国籍
- 登録陸協
- 身高
- 体重
- 人物类型：选手、监督、教练、主务等
- 备注
- 数据状态

### 5.2 Organization：组织

用于表示高中、大学、实业团、公司、俱乐部、赛事组织方。

建议收集字段类型：

- 正式名称
- 简称
- 读音
- 罗马字
- 中文名
- 英文名
- 组织类型：高中、大学、实业团、公司、俱乐部、联盟等
- 所在地
- 都道府县
- 官方网站
- 备注
- 数据状态

注意：

- 大学和大学长距离队伍可以先视为同一组织，后续需要时再拆分
- 实业团队伍和母公司可先用组织类型区分，后续再细分关系

### 5.3 Membership：所属关系

用于表示人物在某时间段属于某组织。

建议收集字段类型：

- 人物
- 组织
- 关系类型：出身、所属、在学、毕业、工作人员等
- 开始年份
- 结束年份
- 年级
- 学部
- 学科
- 期/代
- 队内角色：主将、主务等
- 来源
- 数据状态

V0.1 用它表达：

- 选手当前大学
- 选手出身高中
- 选手年级
- 学部・学科

### 5.4 Personal Best：个人最好成绩

用于表示选手在某项目上的 PB。

建议收集项目：

- 1500m
- 3000m
- 3000mSC
- 5000m
- 10000m
- 10マイル
- ハーフマラソン
- マラソン

建议收集字段类型：

- 人物
- 项目
- 记录
- 创造日期
- 创造赛事
- 创造地点
- 当时所属
- 当时年级或阶段
- 是否高校 PB
- 是否大学 PB
- 来源
- 数据状态

V0.1 页面优先展示：

- 5000m
- 10000m
- ハーフマラソン

其他项目可先录入但不重点展示。

### 5.5 Competition：赛事

用于表示赛事系列。

示例：

- 箱根駅伝
- 出雲駅伝
- 全日本大学駅伝
- 全国高校駅伝
- ニューイヤー駅伝

建议收集字段类型：

- 赛事名称
- 赛事类型
- 主办方
- 地区
- 官方网站
- 备注

V0.1 只需要箱根駅伝作为核心赛事。

### 5.6 Competition Edition：赛事届次

用于表示某一年或某一届赛事。

示例：

- 第102回東京箱根間往復大学駅伝競走

建议收集字段类型：

- 赛事
- 届次
- 年份
- 日期
- 官方名称
- 简称
- 备注
- 来源

### 5.7 Race Result：赛事成绩

用于表示选手在某届赛事中的出场和成绩。

建议收集字段类型：

- 人物
- 所属大学
- 赛事届次
- 区间
- 是否报名
- 是否实际出场
- 是否当日変更
- 区间成绩
- 区间排名
- 综合排名相关信息
- 备注
- 来源
- 数据状态

V0.1 优先用于箱根出场记录。

### 5.8 Source：数据来源

用于记录数据来自哪里。

建议来源类型：

- 大学官网
- 箱根官方
- NTV 箱根页面
- 日本陸連
- 月陸
- 数据站
- 粉丝站
- PDF
- 人工整理

建议收集字段类型：

- 来源名称
- 来源 URL
- 来源类型
- 发布日期，若有
- 访问日期
- 备注
- 可信等级

### 5.9 Name Variant：名称变体

用于管理日文、中文、英文、罗马字、简称、旧字体等。

适用对象：

- 人物
- 组织
- 赛事

建议收集字段类型：

- 目标对象
- 名称
- 语言
- 名称类型：正式名、简称、读音、罗马字、中文译名、英文译名、旧称、媒体写法
- 是否主名称
- 来源

## 6. V0.1 页面设计

### 6.1 首页

首页第一屏应包含：

- 站点名称：襷の系譜
- 副标题
- 搜索框
- 三所大学入口
- 最近更新选手
- 语言切换

首页不是营销页，而是资料入口。

### 6.2 选手列表页

列表支持：

- 按大学筛选
- 按年级筛选
- 按出身高中筛选，若数据足够
- 搜索姓名

展示字段：

- 姓名
- 读音或罗马字
- 大学
- 年级
- 出身高中
- 主要 PB 摘要
- 数据状态

### 6.3 选手详情页

页面结构：

- 基本资料
- 所属与出身
- 主要 PB
- 箱根记录
- 相关选手
- 数据来源

相关选手模块：

- 同大学
- 同高中
- 同年级

V0.1 不做图谱，只做清晰跳转。

### 6.4 管理后台

V0.1 需要一个轻量后台，因为数据维护比公开页面更重要。

后台功能：

- 新增/编辑选手
- 新增/编辑组织
- 新增/编辑所属关系
- 新增/编辑 PB
- 新增/编辑箱根记录
- 新增/编辑来源
- CSV 导入
- 数据状态标记

后台可以先很朴素，但必须好用。

## 7. 数据导入策略

### 7.1 初始数据来源

V0.1 初始数据优先来自：

- 青山学院大学长距离成员页
- 國學院大學成员页
- 中央大学长距离成员页
- 箱根官方报名 PDF
- NTV 箱根页面
- 月陸 Online 名鑑

这些来源覆盖：

- 当前名单
- 姓名读音
- 罗马字
- 学部・学科
- 出身高中
- 出身地
- PB
- 箱根出场记录
- 队伍角色

### 7.2 导入方式

V0.1 不做自动爬虫。

推荐流程：

1. 人工整理 CSV
2. 后台导入 CSV
3. 系统做基础校验
4. 人工确认状态
5. 前台展示 verified / pending 状态

原因：

- 各站结构差异很大
- 数据量早期不大
- 早期重点是确认模型，而不是自动化

### 7.3 数据校验

基础校验包括：

- 同名选手提示
- 同大学同年级重复提示
- PB 时间格式校验
- 成绩项目枚举校验
- 来源缺失提示
- 出身高中不存在时提示创建组织

## 8. 搜索策略

V0.1 使用 PostgreSQL 基础查询即可。

支持：

- 日文姓名搜索
- 罗马字搜索
- 大学筛选
- 高中筛选

后续再引入：

- Meilisearch
- Typesense
- Elasticsearch

搜索服务不应该成为 V0.1 的复杂度来源。

## 9. 多语言实现策略

URL 建议：

```text
/ja
/zh
/en
```

主语言：

- `/ja`

V0.1 翻译范围：

- 导航
- 页面标题
- 字段标签
- 站点说明
- 数据状态
- 来源说明

不要求翻译：

- 所有选手简介
- 所有学校名称
- 所有备注内容

人名和学校名优先展示日文原文，必要时追加罗马字、中文名或英文名。

## 10. 权限与后台安全

V0.1 后台只面向站主使用。

建议：

- 单管理员账号
- 登录后访问 `/admin`
- 不开放注册
- 不开放社区投稿
- 不开放评论

认证可以使用：

- Auth.js

或者更简单的：

- 单管理员密码 + session

如果项目会部署到公开网络，至少需要：

- 后台登录保护
- 管理接口鉴权
- 基础 CSRF 防护
- 环境变量管理密钥

## 11. 部署方案

推荐两种路线。

### 11.1 快速部署

- Vercel
- Neon / Supabase Postgres

适合快速上线和验证。

优点：

- 省运维
- Next.js 支持好
- 数据库托管

缺点：

- 长期成本和数据自主性需要关注

### 11.2 自有服务器部署

- Docker Compose
- Next.js 应用容器
- PostgreSQL 容器
- Nginx / Caddy 反向代理

适合长期个人项目。

优点：

- 自主可控
- 成本稳定
- 方便未来加任务队列、导入脚本、搜索服务

缺点：

- 需要服务器维护

建议：

V0.1 开发期使用本地 Docker PostgreSQL。  
公开验证期可以先上 Vercel + 托管 Postgres。  
如果确定长期维护，再迁到自有服务器。

V0.1 不做：

- 微服务
- 数据仓库
- 图数据库
- 复杂爬虫
- 实时比赛更新

这些都不是第一版风险点。

## 14. 关键风险

### 14.1 数据来源分散

不同来源字段不一致，且可能更新频率不同。

应对：

- 数据模型保留来源和状态
- 先人工整理
- 不急于自动化

### 14.2 同名和名称变体

日文姓名、旧字体、罗马字、中文译名可能不一致。

应对：

- 建立 name variant
- 不把翻译名作为主键
- 所有关系使用内部 ID

### 14.3 字段过多导致后台难用

宽收集可能让后台表单变重。

应对：

- 后台按模块编辑
- 选手基础资料、PB、所属关系、来源分开维护
- V0.1 前台只展示核心字段

### 14.4 版权和引用边界

媒体名鑑和图片存在版权风险。

应对：

- 只收公开事实数据
- 不复制文章正文
- 不直接搬运图片作为核心资产
- 页面保留来源链接

## 15. 实施顺序

建议按以下顺序实施：

1. 初始化 Next.js 项目
2. 接入 PostgreSQL 和 Prisma
3. 建立核心 schema
4. 实现基础 seed 数据
5. 实现选手列表页
6. 实现选手详情页
7. 实现基础搜索
8. 实现轻量后台
9. 实现 CSV 导入
10. 录入三所大学小样本数据
11. 校验页面和数据关系
12. 补充多语言界面
13. 做视觉打磨
14. 准备 V0.1 内部预览
