# Telegram 内容频道矩阵 MVP 技术方案

对应产品方案：[telegram-channel-matrix-mvp-prd.md](./2026-11-05-telegram-channel-matrix-mvp-prd.md)

版本：v0.1  
日期：2026-11-05

本文给出首批 AI / 软件更新与 PC 游戏优惠频道的技术实现建议。目标是用一套可扩展的内容发布系统运行多个独立频道，同时保留来源、规则、Prompt 和观察数据的隔离。

## 1. 技术目标与边界

技术系统负责可靠地完成来源获取、候选标准化、筛选、摘要生成、规则校验、Telegram 发布、运行邮件和数据留存。频道各自决定发布什么、何时发布，以及用什么口吻解释内容。

首版不建设面向读者的 Bot、管理后台、统一品牌站、复杂队列平台或本地 LLM 服务。Telegram Bot 在这里是频道发布身份：由 Bot API 向频道发消息，不向读者提供交互功能。

设计目标：

- 新增频道时主要增加频道配置、来源适配器、规则和 Prompt，不复制一套任务系统。
- 来源失败、LLM 失败或发布失败都能从运行记录定位；一类内容失败不阻止其他频道继续。
- 自动发布前执行确定性规则和结构校验；不把 LLM 自己的“通过”当作安全保证。
- 每条已发布内容能追溯来源、规则版本、Prompt 版本、LLM 模型、校验结果和 Telegram 消息 ID。
- 内容去重及发布状态持久化，进程重启或定时任务重跑不应重复发布。
- 先用小而独立的部署单元验证真实负载，再根据运行数据决定是否迁出当前主机。

## 2. 推荐架构

推荐用 TypeScript / Node.js 单仓库模块化单体，按频道配置驱动；实例上的 systemd timer 每天北京时间 09:00 启动独立批处理容器完成任务，不为每个频道单独部署一份服务。首版用 PostgreSQL 保存运行状态和观察记录，避免只靠进程内存或日志推断任务结果。

```text
Schedule
  -> Source adapters
  -> Candidate normalization and deduplication
  -> Channel rules and eligibility checks
  -> LLM drafting
  -> Deterministic validation
  -> Telegram channel publisher
  -> Post-run email report

PostgreSQL: sources, candidates, runs, prompt/rule versions, publications, metrics
```

主要模块职责：

| 模块 | 职责 |
|---|---|
| Scheduler | 按频道时区及运行窗口创建每日任务；记录每次运行，不依赖机器本地时区 |
| Source adapter | 读取 RSS、官方 API 或商店数据；统一超时、限速、游标、错误和来源许可信息 |
| Normalizer | 将不同来源字段转换成内部 Candidate；保留来源 ID、原始链接、发布时间和必要字段 |
| Deduplication | 按来源稳定 ID、规范化 URL、内容指纹去重；跨来源重复时保留来源关联 |
| Channel policy | 应用频道范围、地区、时效、价格/折扣、排除项和字段必需规则 |
| LLM drafting | 输入已筛选的结构化事实，按版本化 Prompt 生成限定格式的中文草稿 |
| Validator | 检查字段、长度、链接、事实引用、价格/期限和频道格式；失败则跳过，不自动补造信息 |
| Publisher | 通过 Telegram Bot API 发到指定频道；维护幂等状态、重试边界及消息 ID |
| Reporter | 汇总来源、筛选、生成、发布、跳过和异常，发给运营者邮箱 |
| Run reporting | 汇总运行状态、阶段计数和异常，发送运行邮件 |

每个频道配置独立的 channel ID、语言、运行时区、来源列表、采集频率、内容规则、Prompt 版本、发布时间窗口和发布上限。敏感凭据只通过部署环境注入，不进入配置文件或运行记录。

## 3. 来源接入策略

来源按类型实现小型适配器，不先建设通用爬虫框架。首批优先使用官方 RSS / 官方 API；对网页抓取设为明确例外，需要单独确认稳定性、访问限制和再发布条件。

### AI / 软件更新

- OpenAI News RSS、Google AI Blog RSS、Hugging Face Blog RSS 作为首批来源。
- GitHub Changelog 作为低优先级可选来源，须经频道规则筛选。
- 保存 RSS item ID、原文 URL、标题、发布时间、抓取时间及必要的摘要文本；不默认镜像保存全文或图片。
- RSS 缺失稳定 ID 时，使用规范化 URL 与标题/发布时间组合生成指纹，并保留算法版本，便于未来修正。

### PC 游戏优惠

- 对 Steam 中国区商店折扣进行定向查询或解析，保留 App ID、商店链接、币种/地区、当前价、原价、折扣和活动期限（来源确实提供时）。
- 不依赖 GamerPower 或 Epic 页面抓取作为首版发布链路。
- Steam 接入前核对当前可用 API、地区价格和商店数据使用条款。若无法稳定确认地区、价格或折扣有效性，则不自动发布。
- 价格数据必须带采集时间；重复候选若价格或折扣明显变化，应按规则决定更新帖还是仅更新内部记录，首版建议不为同一活动重复发帖。

每个来源适配器须报告本轮开始/结束时间、成功页数或条目数、HTTP 状态类别、重试次数及错误分类。来源成功返回零条与来源不可用是两种不同状态，日报不得把失败写成“今天没有内容”。

## 4. 每日运行流程

1. Scheduler 根据配置为每个频道生成唯一的本地运营日期运行记录。
2. 并行读取互不依赖的来源，但限制全局及来源级并发、请求超时和重试次数。
3. 来源结果标准化后落库，再按唯一键和内容指纹去重。
4. 频道规则对候选作确定性筛选。未满足必填字段、来源可信度、时效、地区或许可条件的项目直接跳过并记录原因。
5. 对通过规则的候选调用 LLM。每条调用绑定 Prompt 版本、模型标识、参数、输入摘要哈希和响应状态；不把无关的用户/频道历史传入模型。
6. 解析结构化输出并执行确定性校验。AI / 软件文案中每个事实须能映射到来源字段或来源原文；游戏价格、地区、折扣、活动期由采集数据填充，不允许 LLM 改写这些数值。
7. 将通过校验的条目按频道组装为当日一期「每日精选」，每期最多 5 条，不凑数；没有合格条目不发空稿。发布前逐条复查候选未过期、未发布以及 Steam 价格有效性，再检查整期目标频道、长度、HTML 转义及各条目的来源链接。超限时减少完整条目，不截断段落或 HTML，也不默认拆帖。
8. Telegram 返回成功后保存 message_id、发送时间及发布状态；将无法确认是否送达的网络超时标成 uncertain，不盲目无限重发。
9. 运行结束生成邮件，列明每个频道和来源的状态、候选数、去重数、通过数、跳过原因、LLM 错误、发布数、失败和不确定发送。

自动发布策略不包含逐条审批。每频道每日一次集中采集、筛选和组稿，发布单元为一期包含多条内容的每日精选，不按候选分别发帖。Steam 发送前的定向价格复查不等于再次进行全量采集。每频道每日最多一期；超限候选保留并记录未入选原因，不在同一日无限补发。

## 5. Prompt 与内容契约

Prompt 按频道分别版本化，公共部分只负责输出结构和通用事实约束，不把两个垂直频道的选品标准混成一个长 Prompt。每次运行固化 Prompt 版本和模型标识，避免在线编辑造成同一轮结果不可复现。

LLM 输入采用明确字段白名单，例如：来源标题、来源摘要/允许引用的正文片段、原文链接、发布时间、来源名称、结构化业务字段、频道规则摘要。模型输出使用 JSON schema 或等价结构，至少包含：

- `decision`: `publish` 或 `skip`，仅作为辅助信号，不覆盖规则引擎；
- `title`、`body`：符合频道格式的简体中文内容；
- `claims`: 文案事实及其对应的来源字段或引用片段；
- `uncertainties`: 无法确认的字段或限制；
- `reason`: 简短的编辑理由，供观察和调试，不直接发给读者。

验证器负责检查可追溯事实、地区、时间、格式、禁用内容、必要字段及 Telegram 长度。验证器无法判断“是否足够吸引人”或事实本身的真实性；这依赖上游来源可信度，未来也可通过人工抽查和读者反馈补充判断。首版不让模型自行搜索或补充输入以外的事实。

Prompt A/B 测试不属于 MVP。MVP 只保存版本并让已发布内容可追溯到实际使用的 Prompt；未来若有足够内容和增长信号，再设计分组与比较口径。

## 6. 核心数据与幂等

建议的核心实体：

| 实体 | 关键字段与用途 |
|---|---|
| Channel | 稳定 ID、目标 chat ID、语言、时区、开关、配置版本 |
| Source | 来源类型、来源配置引用、许可备注、上次成功/失败时间 |
| ChannelSource | 频道与来源关系、优先级、启用状态及来源级规则 |
| Candidate | 来源 ID、规范化 URL、字段 JSON、发布时间、指纹、状态 |
| CandidateSource | 跨来源重复时保留每个来源及其证据链接 |
| ContentDraft | Candidate、频道、规则版本、Prompt 版本、模型、结构化文案、验证状态 |
| Run | 频道、运营日期、开始/结束、各阶段计数、最终状态和错误摘要 |
| Publication | Candidate/草稿、频道、幂等键、状态、Telegram message_id、发送时间 |
| PromptVersion | 频道、版本号、正文哈希、创建时间和启用状态 |

发布幂等键使用 `channel_id + operating_date + daily_digest`，在数据库唯一约束，避免同日重跑产生第二期。另以关联表记录本期的 Candidate、ContentDraft 和条目顺序，候选跨日去重保持独立。发布记录状态包括 `prepared`、`sending`、`sent`、`failed`、`uncertain`。向 Telegram 发送前先持久化 `sending`；请求明确失败可有限重试，连接中断但无法确认 Telegram 是否接收时转 `uncertain`，通过核查或人工命令处理，不能声称 Bot API 提供严格一次投递。

候选和草稿只保留支持去重、复盘和观察所需的数据。来源条款若不允许存储正文，则只保存最小元数据、短期处理文本或内容哈希，并设置清理期限。敏感的 Bot Token、LLM API Key、SMTP 密码不写入数据库。

## 7. MVP 运行记录

MVP 只记录保证自动化可运行和可排障所需的信息，不建设频道增长分析或读者反馈采集。每日邮件报告展示运行状态、来源成功/失败、候选数、去重数、跳过原因、生成数、发布数及发送异常；这些数据用于判断任务是否正常完成，不用于判断频道是否增长。

持久化运行记录保留来源、规则版本、Prompt 版本、模型标识、Telegram 消息 ID、阶段计数和错误类别，支持去重、重试和故障定位。LLM 调用用量或费用可在服务商账单中查看，不设置产品内预算上限、费用闸门或达到额度后自动停机。

帖子阅读量、订阅变化、转发、外链点击、Prompt A/B 效果比较和频道加码/淘汰分析均不属于 MVP。待频道出现值得分析的实际增长或内容供给后，再单独讨论采集方式与观察口径；在此之前不建设浏览量采集器、追踪短链或分析导出。

## 8. 部署与成本建议

### 推荐阶段

建议分两步：

1. 内部试运行阶段复用 Ubuntu-3，但以独立应用容器、独立 Compose project、独立数据库和账号隔离；只跑低并发定时批处理，LLM 使用外部 API，不在主机运行模型。此阶段用于验证真实 CPU/内存峰值、来源稳定性、LLM 单条成本和发布量。
2. 当频道数量、任务密度或主机资源余量触及告警线，或同机故障隔离不足以接受时，再迁至独立小型实例/托管容器。部署设计保留镜像、迁移、备份和配置边界，避免业务逻辑绑定当前主机。

当前盘点显示 Ubuntu-3 为 2 vCPU、2 GB RAM，检查时约有 750 MB 可用内存且没有 swap；已有多个项目和 PostgreSQL。频道任务是间歇性轻量负载，初期未必需要另购机器，但可用余量有限，必须以实际完整运行峰值验证；不得只看空闲时状态。试运行前应核实当前生产资源、容器限额、日志及备份空间，再设保守容器上限并确认其不会挤压现有服务。若无法给已有服务留下足够余量，则改用独立机器，不以 OOM 后再迁移作为计划。

### 隔离方式

- 独立工作目录、Compose project、应用容器、发布镜像、环境文件和日志限额。
- 数据库使用独立数据库及最小权限账号；可先共用 PostgreSQL 服务，不新增 Redis。数据库负载低且表量有限时无需专门数据库实例。
- 应用不暴露公网端口；批处理仅需出站访问来源、Telegram、LLM 和 SMTP。若 Telegram 发送采用 Bot API 直接 HTTPS，不需要新增 webhook 路由。
- 每频道配置开关；每来源独立启停。部署/迁移不触碰其他项目的容器、网络、卷、防火墙或 Nginx 路由。
- 镜像在 CI 构建，不在 2 GB 服务器上编译依赖。

### 可控成本

- LLM 只处理通过来源及确定性规则的候选；限制单次输入长度和故障重试，避免异常循环调用。MVP 不设置费用预算上限或费用触发的自动停机。
- 可在每次运行中批量处理候选，但要维持单候选校验与失败隔离。模型标识纳入运行记录。
- RSS 和公开免费接口按其条款及限额低频轮询，使用 ETag/Last-Modified、增量游标和缓存，避免无意义重复获取。
- 初期不购买独立队列、分析平台、代理池或爬虫服务；遇到明确覆盖缺口再评估。
- 每月核算 LLM、邮件、主机增量资源和人工复核时间，区分现有固定机器成本与该项目的边际成本。

## 9. 失败处理与安全

- 单来源失败：其他来源和频道可继续；对应来源状态为失败，不生成“无更新”结论。
- RSS/API 限速：遵循 Retry-After；超时与 5xx 有上限退避；畸形数据隔离，不推进错误游标。
- LLM 超时、拒绝或 JSON 无效：有限重试一次后跳过，保留错误类型和候选，不循环重写。
- 校验失败：不发布，记录确定性失败规则；必要时邮件摘要，不将原始敏感堆栈外发。
- Telegram 429：遵循 retry_after；明确权限/频道错误停止该频道并告警；发送状态不明则进入 uncertain。
- 邮件失败：独立告警日志和限次重试；不影响已发布状态，不把邮件失败误报成整个频道发布失败。
- 网络出站最小化并使用 HTTPS；日志过滤 Token、完整连接串、API Key 和不必要的原文正文。
- Telegram Bot 至少只加入目标频道并授予发帖权限，不给管理员权限；每个频道 ID 在配置中显式核对，避免测试内容发到生产频道。
- 发布前检查内容长度和 HTML 转义；原始来源链接在消息中清楚展示。

## 10. 测试与上线验收

本地使用固定来源 fixture、模拟 LLM 和 Telegram API 做可重复测试；CI 覆盖迁移、类型检查、单元测试、集成测试和容器构建。测试数据库与生产隔离。

关键测试：

- 来源分页、条件请求、限速、超时、畸形项及零结果/失败区分。
- 同一条目重复获取、跨来源重复、不同频道规则各自筛选。
- Prompt 输出结构错误、无证据事实、地区/价格/截止时间字段缺失和过期候选。
- Telegram 文本格式、长度、HTML 转义、429、权限失败及发送结果不确定。
- 同一日任务重复启动、进程中断恢复、唯一发布键和不同 Prompt 版本追溯。
- 邮件汇总成功/失败，且邮件发送故障不改变 Telegram 发布记录。
- 两个频道并行时的隔离、每频道开关和单频道失败后的继续执行。

开放给真实频道前完成：核对来源使用条款及关键字段；将 Bot 加入测试频道验证发帖权限和格式；测试小批候选的 LLM 输出及成本；验证邮件收件；连续观察若干个完整定时周期的来源状态、RSS/价格有效性、运行时资源及浏览数据可采集性。自动发布可以在通过规则后启用，但应先使用低每日上限。

## 11. 实施顺序与待定项

建议实施顺序：

1. 确定仓库、运行环境和密钥管理边界；创建数据库 schema 与通用运行记录。
2. 先实现 AI / 软件官方 RSS 适配器，验证候选去重、规则、摘要、Telegram 测试频道及邮件闭环。
3. 加入 Steam 中国区价格适配器及价格/活动期校验；在数据可靠性通过验收前不自动发折扣帖。
4. 完成运行邮件及运行记录验收；读者表现采集留待 MVP 之后评估。
5. 保存 Prompt 版本及每条内容实际使用的版本；Prompt A/B 效果分析留待后续阶段。
6. 根据峰值资源、失败恢复和增量成本决定是否迁机及是否拆分 worker。

实现前需要逐项确认的参数：

- 具体收件邮箱及 SMTP/邮件服务；
- 已确定：Asia/Shanghai 每天 09:00 触发；每频道每日最多一期，处理完成后发送；
- LLM 服务、模型候选及密钥保管方式；

## 12. 已确认的实例运行与补跑规则（2026-11-05）

用户已授权部署及一次线上实际触发。生产入口不接受日期/force 覆盖，实例定时和 Codex 补跑都调用同一服务及数据库。systemd timer 使用 `OnCalendar=*-*-* 09:00:00 Asia/Shanghai`、`Persistent=true`；停机后按实际恢复日期补跑，不回补历史帖子。应用批处理结束退出，不增加公网服务端口。

生产 PostgreSQL 以 `channel + operating_date + daily_digest` 主键约束每日唯一发送；数据库 advisory lock 串行化整轮任务。发送前事务提交 sending、完整待发载荷和入选候选；只有 Telegram 成功回执含匹配频道及可靠 message_id 后才写 sent。发送返回不明记 uncertain，数据库写回中断保留 sending；两者都禁止自动或普通命令重发。明确 API 拒绝记 failed，允许经同一入口补跑。删除频道消息不删发送历史，也不解锁当天名额。机器人与频道权限检查在发送前完成。

本地文件回执只用于历史连通和排版样稿，不是生产发送记录。生产镜像移除这些历史测试发送入口；不建设人工发帖界面。常规人工补跑由 Codex 在实例执行 `systemctl start telegram-channel-matrix.service`。

每轮保存来源状态、候选、Prompt 哈希、模型结果、价格复查及运行报告；邮件报告独立于 Telegram 状态。systemd 超时/异常退出钩子尝试补发故障邮件并备份本项目数据库。邮件提交 SMTP 不代表收件人已阅读，来源或模型失败不应冒充“无内容”。
